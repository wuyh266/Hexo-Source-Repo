让模型说一句“记住了”并不难。麻烦的是，把程序关掉，再开一次，它到底还能拿到什么？

如果偏好只留在上一次的消息列表里，新会话未必能看到；如果保存到了文件，却没有放进下一次模型输入，模型同样无从得知。

10 月 29 日，AgentHub 的独立课程示例把这条路径补得更直观了：先结束一次会话，提取并保存候选记忆；再用新进程打开同一个文件，召回相关记录，送进新的工作模型输入。

这篇讲的是独立的 `s09_memory` 示例，尚未接入主入口 `cmd/agenthub`。默认模型回复是固定的，重点在于检查宿主有没有把数据接过去，不能据此认定真实模型已经具备可靠的长期记忆效果。

## 先结束当前回复，再考虑保存什么

示例使用一条偏好：“以后退货回答要保留来源，并说明已确认的适用条件。”

当前回复与持久保存分开处理。会话正常结束以后，程序才进入提取阶段。下面是已有 `session`、`ctx` 和 `query` 之后的实际片段：

```go
out, err := session.Run(ctx, query)
if err != nil {
    return err
}
if out.Status != "completed" {
    return fmt.Errorf("会话没有正常完成，跳过记忆提取: %s", out.Status)
}
```

**作用：** 运行当前会话，只有它正常完成时才继续提取记忆。会话失败或未完成，不进入后面的保存路径。

**技术栈：** Go 的错误处理，以及独立课程模块中的 Session 和 Outcome。这里使用课程自己的运行时，并非主项目的文本 ReAct 循环。

**关键用法：** `session.Run` 返回结果与错误；`out.Status` 用于区分正常完成和其他结束状态。前面的回复只能表达当前处理结果，不能在尚未写入文件时，就当作持久保存已经成功。

示例给当前回复模型的系统说明也明确要求：不要声称记忆已经持久保存。这样，一句应答与一次文件写入就有了各自的位置。

## 提取器生成候选，存储层再决定能不能保存

正常回复结束后，示例准备一条固定候选，用它观察提取与存储之间的连接：

```go
candidate := []rt.Memory{{
    Name:        "answer-source",
    Type:        "user",
    Description: "退货答复偏好",
    Body:        "退货回答要保留来源并说明已确认的适用条件。",
}}
extractor := &rt.Scripted{Replies: []rt.Reply{{Text: string(rt.MustJSON(candidate))}}}
if err = memory.Extract(ctx, session.Messages, rt.ExtractorWithModel(rt.ModelFromEnv(extractor))); err != nil {
    return err
}
persisted, err := rt.OpenMemory(path)
if err != nil {
    return err
}
```

**作用：** 让独立提取器产生候选记录，经存储层校验后写入，再新建存储实例从磁盘重读。默认候选是固定数据，用于观察宿主流程。

**技术栈：** Go、JSON、课程中的 `Scripted` 模型、`MemoryStore` 与文件存储函数。

**关键用法：** `ExtractorWithModel` 把模型包装成候选提取器，不给它工具执行能力；`Extract` 接收会话消息并逐条调用存储校验。`Name` 标识记录，`Type` 表示记忆类别，`Description` 便于检索，`Body` 保存正文。`OpenMemory(path)` 创建新的存储实例，读取同一路径。

这里仍有两层需要分别看。

提取器输出 JSON，不代表内容已经可靠。存储层会检查名称、允许的类型和非空正文；同名记录替换原记录，其他记录保留。写盘成功后，才更新当前实例的内存状态。

而默认候选由代码预先给出，也就不能用这次运行证明模型能从任意对话里提取出合适的长期偏好。它验证的是候选怎样经过接口走到文件里。

## 新会话只读文件，不接走旧消息列表

读取阶段重新打开存储，再按关键词召回：

```go
recalled := memory.Recall("退货", 5, 1000)
fmt.Printf("[会话 B] 磁盘召回 %d 条: %+v\n", len(recalled), recalled)
```

**作用：** 从当前存储实例中选出与退货相关的记忆，供新会话使用。这里打印的是召回结果，尚未等同于模型已经收到它。

**技术栈：** Go、课程中的确定性关键词检索和 Unicode 字符计数。

**关键用法：** `Recall(query, k, maxChars)` 的第一个参数是查询；`5` 限制检索候选数量，`1000` 限制最终选入记忆的正文字符总量。超过正文预算的记录会被跳过。这个预算没有包含完整 JSON、其他消息或 Token，不能直接当作模型输入长度上限。

当前查询词明确写成了“退货”。检索在记忆描述与正文中按关键词寻找相关项，没有实现自然语言的语义选择。无关任务可能返回空列表，文件不存在时也可以得到空存储；损坏的已有文件则不能假装读取成功。

一次新会话不必复制全部旧对话。示例只从文件取回相关背景，同时保留本次用户提出的范围要求。

## 召回以后，还要真的放进模型输入

示例在工作模型入口加了一层观察包装，打印它实际收到的系统说明与首轮消息数量。下面是使用这个 `observed` 模型、召回结果和当前问题建立会话的部分：

```go
session := rt.NewSession(observed, rt.KnowledgeTool(rt.DemoPolicies))
session.System = "你是政策问答助手。政策结论必须依据知识检索结果。以下记忆是背景；与当前用户要求冲突时，当前要求优先。\n召回记忆: " + string(rt.MustJSON(recalled))
out, err := session.Run(ctx, query)
if err != nil {
    return err
}
rt.PrintSession(session, out)
```

**作用：** 将召回记忆放入真正传给工作模型的系统说明，再开始当前问题的运行。政策资料仍由知识工具提供，偏好记录只作为背景。

**技术栈：** Go 的模型接口包装、JSON 序列化，以及独立课程的 Session 和知识工具。

**关键用法：** `rt.MustJSON(recalled)` 序列化选中的记录；设置 `session.System` 后，再调用 `Run`。`observed` 是示例已经准备好的模型包装，用于检查实际输入。`PrintSession` 展示运行后的消息与结果，不负责把记忆注入模型。

这一处连接很关键。保存文件、打印召回结果、写入工作模型输入，是三个不同的动作。前两个都完成，仍然可能漏掉第三个。

示例也写明当前要求优先：过去保存了偏好，并不表示可以忽略现在的任务边界。不过，这句系统说明本身不是强制执行器。默认回答仍是固定回复，不能据此证明真实模型一定会遵循偏好与优先级。

## 分成两个进程跑，才看得清数据从哪里来

进入独立课程模块根目录后，可以分别保存与读取：

```powershell
$env:COURSE_LIVE = "0"
go run ./s09_memory -mode save -store .\.course-data\memory-walkthrough\memory.json
go run ./s09_memory -mode ask -store .\.course-data\memory-walkthrough\memory.json
```

**作用：** 先完成保存，再启动另一个进程从同一个文件读取，让两次运行通过磁盘交换数据，而不是共用上一次的内存消息。

**技术栈：** PowerShell、Go 命令行工具和本地 JSON 文件；模型使用固定回复，不发起真实模型请求。

**关键用法：** `-mode save` 执行当前会话后的提取与写入；`-mode ask` 新建存储与会话，只做召回和回答；`-store` 指定共同文件。`COURSE_LIVE=0` 使用固定模型。也可以用 `-mode demo` 在一次程序运行中连续观察两个阶段。

这次验证除了查看文件内容，还检查了实际工作模型入口：召回正文确实进入系统说明，首轮消息只包含当前用户请求。只读的 `ask` 不会修改记忆文件，已有其他记录也没有被这次保存整份抹掉。

## 这一版的优点

- **数据路径可追踪。** 从正常回复、候选提取，到写盘、重开文件和注入新会话，每一步都能找到实际调用。
- **新会话不依赖旧消息对象。** 分开运行保存与读取，能检验持久化是否真正参与了流程。
- **召回有明确范围。** 只选择相关记忆，并对条数和正文长度设置限制，避免无条件塞入所有记录。

## 还没有补齐的地方

- **模型效果没有得到验证。** 默认提取候选和回答都是固定回复，语义提取、召回质量及偏好遵循仍需用真实模型和任务评估。
- **存储还是轻量实现。** 提取结果逐条保存，没有整批事务或失败回滚；进程内互斥也不提供多进程文件锁。
- **记录治理仍需完善。** 当前以同名替换做最小整理，尚未建立来源审阅、版本冲突、过期清理或多用户隔离机制。
- **仍是独立示例。** 它没有把跨会话记忆接到主入口 `cmd/agenthub`，不能据此声称现有业务 CLI 已经获得这项能力。

以后再看到“记住了”这句话，我会先往下追一追：它保存到了哪里，新会话怎样找回，以及真正发给模型的输入里有没有这份内容。把这些动作连上，才有继续讨论记忆效果的基础。
